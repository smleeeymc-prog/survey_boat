참여자들이 남긴 문장이 배 한 척씩으로 바뀌어 한 바다에 모이는 전시용 송출 화면입니다.

기존 도메인이 붙어 있는 프로젝트는 계속 main을 봅니다. 서로 건드리지 않습니다.

main              온보딩 씬 → 기존 도메인

새 프로젝트 만들기

  1. Vercel → Add New… → Project → 같은 레포(survey_boat) 선택
  2. Root Directory를 statistics 로 지정 — 이게 전부입니다. Framework Preset은 Other, Build Command·Install Command는 비워 둡니다 (정적 파일이라 빌드가 없습니다. statistics/vercel.json이 이미 그렇게 잡아 뒀습니다)
  3. Settings → Git → Production Branch를 statistics-main 으로 바꿉니다. (기본값이 main이라 이걸 안 바꾸면 statistics/가 없는 커밋을 배포하려 합니다)
  4. Settings → Domains에서 새 도메인을 붙입니다.

결과: 새도메인/ = 머무름의 지도, 기존도메인/ = 온보딩(손대지 않음).

배포 전에 한 번 볼 것

  • three.js를 unpkg CDN에서 받습니다. unpkg가 죽으면 화면도 죽습니다. 전시 당일 리스크를 없애려면 three.module.js와 GLTFLoader.js를 레포에 넣고 importmap을 그쪽으로 돌리는 게 안전합니다(약 1.4MB). 지금은 온보딩 씬과 같은 방식을 유지했습니다.
  • 캐시: HTML·JS·CSS는 must-revalidate, GLB는 1년 immutable로 잡아 뒀습니다. 전시 중 코드를 고치면 새로고침만으로 반영되고, 무거운 모델은 다시 안 받습니다.

항목결정근거

카메라고정 (무조작)전시장 TV/프로젝터에 입력장치가 없음. 배가 흐르는 연출이라 카메라까지 움직이면 "화면 끝에서 등장 → 반대쪽 퇴장" 규칙이 깨짐. ?interactive=1로 리허설용 조작만 열어둠

흐름 — 배는 어떻게 움직이나

배는 전부 같은 방향으로, 같은 속도로 흐릅니다. 화면 왼쪽 끝에서 나타나 오른쪽으로
빠지고, 띠 폭(FLOW_CORRIDOR_W = 80)을 다 지나면 반대편 끝으로 감겨 다시 들어옵니다.

속도는 상수로 박지 않고 "기준 깊이의 배가 40초에 화면을 건넌다"로 정의하고
카메라 화각에서 역산합니다(FLOW_CROSS_SEC, FLOW_REF_DEPTH). 화면 폭은 기기
화면비마다 다르기 때문입니다. 세로 화면(1080×1920) 실측:

카메라 앞 거리화면 가로 폭횡단 시간
10 (화면 아래끝)6.524초
158.632초
20 (기준)10.940초
30 (화면 세로 중앙)15.758초
48 (가장 먼 배)24.690초

속도를 하나로 통일한 게 핵심입니다. 깊이마다 속도를 달리 주면 원근이 사라져
평면 스크롤처럼 보입니다. 가까운 배가 빨리, 먼 배가 천천히 지나가는 게 깊이감입니다.
띠 폭이 화면보다 넉넉해서 감기는 순간은 언제나 화면 밖이고, selfcheck.js가 이걸
화면비마다 검산합니다.

한 번에 화면에 보이는 배는 80척 중 약 13척입니다. 나머지는 띠의 화면 밖 구간에 있고,
약 5분 주기로 다시 들어옵니다.

표현 채널 — 지금은 난수

어떤 답변이 배의 무엇을 바꿀지가 아직 확정되지 않아서, 채널 값을 실제 답변이 아니라
난수에서 뽑고 있습니다. config.js의 한 줄로 바뀝니다:

export const STYLE_SOURCE = "random";   // "random" | "record"

난수는 record_id를 시드로 한 고정 난수입니다 — 매 프레임 새로 뽑으면 색이 깜빡이고,
매 로드마다 새로 뽑으면 전시 중 재시작할 때 바다가 통째로 달라집니다. 지금 방식이면
"그 기록의 배"는 언제 봐도 같은 배입니다.

중요: 난수인 건 배의 모습뿐입니다. 상단 패널의 누적 수와 통계(키워드·상태·지역
분포)는 지금도 실제 기록에서 집계합니다.

채널어떻게비용
캐빈 색instanceColor (재질 색을 흰색으로 두고 색 전체를 인스턴스가 들고 감)공짜
선체 색조instanceColor (GLB 원본 색에 흰색 근처 색조를 곱함 — 원본 색을 안 버림)공짜
갑판 소품갈매기 / 구명튜브. 파츠마다 인스턴스 그룹 1개draw call +1씩

매핑을 바꾸거나 채널을 늘릴 때 손대는 파일은 style.js 하나입니다. 새 채널에

따라 바다 중심에서의 거리와 움직임이 달랐습니다. 채널 구성이 아직 변동될 수 있다고 해서

그대로 가져온 것 — Gerstner 파도 3개(파장 2.2/1.3/0.8)와 그 상수, 플랫 셰이딩(dFdx/dFdy),

바꾼 것 (3곳뿐입니다)

  1. 재중심이 1축 → 2축. 온보딩은 배가 +X로만 나아가서 uBoatX(float) 하나면 됐습니다. 지도는 카메라가 XZ 평면을 자유롭게 흐르므로 uCenter(vec2)로 바꿨습니다. 수식은 그대로입니다. WAVE_WRAP_DOMAIN = 1144가 Z축에서도 공배수인지 검산해 봤고, 맞습니다 (X: 520/440/1001, Z: 78/748/572 — 전부 정수). selfcheck.js가 로드마다 다시 검산합니다.
  2. 유리병 클리핑(uClip*) 제거. 지도엔 병이 없습니다.
  3. 스케일·카메라·인스턴싱 구조. 배 크기 3.38 → 1.5, FOV 34 → 50, 타일 31.5 → 190, 안개 범위 확대. 재질·색·지오메트리는 손대지 않았습니다.

알아둘 것 — 인수인계 문서와 실제가 다른 점

  • Scene.glb의 위치: 문서는 루트라고 했지만 실제로는 assets/Scene.glb입니다. 처음에는 복사하지 않고 ../assets/Scene.glb로만 참조했습니다(사본이 갈라질 위험이 없어서). 지도를 자기 도메인에 따로 올리기로 하면서 사본이 필요해졌습니다 — Vercel의 Root Directory는 그 폴더 밖의 파일을 배포에 포함하지 않습니다. 지금은 statistics/assets/에 사본을 두고, 코드가 후보 두 경로를 순서대로 시도합니다. 드리프트는 sync-model.mjs로 막습니다(위 "Vercel 배포" 참고).
  • 배의 폴리곤 수: 문서는 282 tri라고 했지만 실제 Ship 노드는 1,302 tri입니다 (Ship Body 1226 + Funnel 40 + Funnel step 24 + Cabin 12). 갈매기(1,472)와 튜브(312)까지 더하면 배 1척이 최대 3,086 tri, 80척이면 약 247,000 tri입니다. draw call이 9로 고정이라 현대 GPU에는 여전히 여유가 있지만, 문서의 "22,560 tri" 추정보다 한 자리 큽니다.
  • 키워드 목록: 시안 스크린샷에는 비용이 있지만 온보딩(../index.html)의 실제 KEYWORDS에는 없습니다. 집계가 갈라지면 안 되므로 온보딩 쪽을 정본으로 삼았습니다.
  • GLB의 Cabin 노드에는 재질이 없습니다. 그러면 GLTFLoader가 기본 재질을 만들어 주는데, 그 기본값이 metalness: 1(완전 금속)입니다. 금속은 확산광이 없고 환경맵 반사만 보이는데 이 씬에는 환경맵이 없어서, 직사광이 강한 낮에는 색이 스페큘러로 어른거리다가 밤 팔레트에서는 캐빈이 통째로 새까매집니다 — 즉 "키워드 → 캐빈 색" 규칙이 기본 설정에서 아무 일도 안 합니다. 누가 의도해서 칠한 재질이 아니라 로더의 기본값이므로, 캐빈 그룹에 한해 metalness: 0으로 되돌렸습니다(색·지오메트리는 그대로). 온보딩 씬(../index.html)에도 같은 증상이 잠재해 있습니다 — 거기는 밝은 시간대가 기본이라 아직 드러나지 않았을 뿐이고, 사용자가 '나눈 적 없음'을 골라 밤이 되면 캐빈 색이 사라집니다. 온보딩 쪽은 이번 작업 범위 밖이라 건드리지 않았습니다.
  • instanceColor는 material.vertexColors = true 없이는 조용히 버려집니다. three.js의 color_vertex 청크는 USE_INSTANCING_COLOR만으로도 vColor를 채우지만, color_fragment 청크는 USE_COLOR(= vertexColors)일 때만 그 값을 곱합니다. 그리고 vertexColors를 켜면 지오메트리의 color 어트리뷰트도 같이 읽으므로, 전부 1인 어트리뷰트를 깔아 둬야 새까매지지 않습니다. 둘 다 fleet.js에 주석으로 남겼습니다.

남은 일

  1. 백엔드 (제일 큰 덩어리). 지금은 MockStore가 가짜 기록을 만들어 냅니다. 화면이 저장소에 요구하는 건 세 가지뿐입니다 — onReady(records) / onInsert(record) / onRemove(recordId). store.js에 Supabase·Firestore 두 경우의 배선이 주석으로 적혀 있고, 정해지면 main.js의 저장소 한 줄만 갈아끼우면 씬 쪽은 손댈 게 없습니다.
  2. 어느 쪽이든 공개 조건(consent_public && moderation_status === "public")은 서버에서 걸어야 합니다. 비공개 문장이 브라우저까지 내려온 뒤 JS가 거르는 구조면 개발자도구만 열면 다 보입니다.
  3. Firestore를 쓴다면: 첫 스냅샷이 기존 문서 전부를 added로 줍니다. 그대로 두면 시작할 때 수십 척이 한 척씩 등장 연출을 하며 쏟아집니다. 첫 스냅샷만 모아서 onReady로 넘겨야 합니다.
  4. 관리자 화면 (문장 숨김·금칙어 확인). 화면 쪽은 onRemove만 받으면 즉시 반영됩니다.
  5. 인터넷 장애 대비 임시 로컬 저장·재전송. 제출 쪽(온보딩) 몫입니다.
  6. 실기기 프레임 측정. 전시장에서 쓸 TV/태블릿에서 ?debug=1로 한 번 재보고 ?glass=를 고정할 것. Chromium 계열이 아니면 굴절은 자동으로 꺼집니다.
  7. 표현 채널 확정. STYLE_SOURCE를 "record"로 바꾸고 style.js의 fromRecord 쪽을 채우면 됩니다. 지역 → 선체 색조 매핑은 자리만 비워 뒀습니다.
  8. 폰트. 지금은 시스템 폰트 스택(온보딩과 동일)입니다. 전시장 기기에 따라 초대형 숫자의 인상이 달라질 수 있어서, 웹폰트를 쓸 거면 오프라인 대비로 파일을 레포에 넣는 편이 안전합니다.
