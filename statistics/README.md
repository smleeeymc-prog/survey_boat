# 머무름의 지도 (statistics/)

참여자들이 남긴 문장이 배 한 척씩으로 바뀌어 한 바다에 모이는 **전시용 송출 화면**입니다.
루트의 온보딩 씬(`../index.html`)이 "참여자 1명이 자기 배 1척을 보는 화면"이라면, 이 화면은
그 배들이 전부 모여 있는 화면입니다.

```
statistics/
├─ index.html        화면 골격 · importmap · 리퀴드 글래스 SVG 필터
├─ vercel.json       이 폴더만 따로 배포할 때의 설정 (레포 루트에는 두지 않는다)
├─ shared/           ★ 온보딩 씬(../index.html)과 이 화면이 같이 읽는 원본
│  ├─ ocean-core.js      파도 표 · 셰이더 GLSL · 파고 계산 · 랩 도메인
│  ├─ palette.js         시간대 팔레트 · 지역 색
│  ├─ ship-tokens.js     뱃머리 보정 · 흘수
│  ├─ glb-nodes.js       GLB 노드 이름 · 키워드 → 배의 요소 · 뱃전 요소 · 클로버 규격
│  ├─ look-tokens.js     조명 비율 · 거칠기 상한 · 구운 AO 세기 (두 화면 톤 맞추기)
│  ├─ tokens.css         UI 색 · 화면 색보정(--scene-grade) · 비네트
│  ├─ deps.js            three 버전 (두 importmap 과 대조)

│  ├─ record-schema.js   기록 한 건의 모양·검사 (클래식 스크립트 — 보안 규칙도 여기서 생성)

├─ tools/

│  ├─ check-insights.mjs     통계의 "한 줄 결론"이 틀리지 않는지 검사 (node, 브라우저 불필요)

├─ css/
│  ├─ panel.css      위쪽 제목 · 가운데 통계 카드 · 아래 방금 도착한 문장 (설문 B′ 톤) · 모션 · 반응형
│  ├─ stats.css      통계 표시 모듈 전용 — js/stats/views.js 와 한 쌍
│  └─ tilt-shift.css 화면 위아래 흐림(미니어처) — 설문 .tiltBlur 와 같은 모양

   ├─ panel.js       화면의 두 시간(풍경 ↔ 통계) · 새 배가 끼어들 때의 규칙 · 누적 수 · 카드 채우기
   ├─ stats/         통계 — 패널 껍데기와 분리돼 있다 (아래 "통계" 참고)
   │  ├─ metrics.js     무엇을 세는가
   │  ├─ insights.js    어떻게 읽는가 (값 · 한 줄 결론 · 강조할 것)
   │  ├─ views.js       어떻게 그리는가
   │  ├─ index.js       무엇을 어떻게, 어떤 순서로 (장 목록)
   │  └─ text.js        조사(은/는·이/가…) · 퍼센트 · 날짜 글자 도구
   ├─ store.js       기록 저장소 — FirestoreStore(실DB) / MockStore(설정이 비었을 때), pickStore
```

## 시안 보기 — 서버 없이

`statistics/tools/build-standalone.mjs`가 **더블클릭하면 열리는 파일 하나**를 뽑아 줍니다.
three.js·GLTFLoader·Scene.glb·앱 코드를 전부 파일 안에 넣어서, 로컬 서버도 CDN도
필요 없습니다. 세로 9:16 액자 안에서 돌기 때문에 가로 모니터에서도 전시 화면 그대로 보입니다.

```bash
npm i three@0.160.1                                    # 한 번만
node statistics/tools/build-standalone.mjs             # → 머무름의지도_시안.html
```

> 이 프로젝트에 빌드 도구가 생긴 게 아닙니다. `statistics/`는 그대로 순수 vanilla이고,
> 이 스크립트는 앱을 빌드하지 않습니다. 리뷰용 사본을 뽑을 뿐이라, 씬 문서와 원본의
> 차이는 스크립트 안 `REWRITES`에 적힌 세 군데뿐입니다(GLB를 fetch 대신 parse,
> iframe에는 location.search가 없어 파라미터를 따로 받음).

## 실행 — 원본 그대로

`file://`로 열면 GLB fetch가 CORS로 막힙니다. 로컬 서버가 필요합니다.

```bash
python3 -m http.server 8000      # 레포 루트에서
# → http://localhost:8000/statistics/
```

GitHub Pages에 올라가 있으면 `/statistics/` 경로로 바로 열립니다.

### 쿼리 파라미터

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `time` | `day` | 시간대 팔레트 (`day` / `afternoon` / `evening` / `night`). 기본값은 설문 페이지의 `INITIAL_TIME_KEY`와 같다 |
| `glass` | (자동) | 유리 단계 고정 (`lens` / `blur` / `flat`). 안 주면 워치독이 판단 |
| `debug` | – | `1`이면 fps·draw call·인스턴스 수 오버레이 |
| `interactive` | – | `1`이면 드래그로 시점 조작 (리허설용, 전시 기본값은 무조작) |
| `mock` | – | `1`이면 DB 설정이 있어도 목업으로 (리허설·시안용) |
| `emu` | – | `1`이면 로컬 Firestore 에뮬레이터 (localhost에서만 켜진다 — `HANDOFF.md` 13.8) |
| `seed` | `46` | 목업: 시작할 때 이미 쌓여 있는 기록 수 |
| `interval` | `14` | 목업: 새 기록이 들어오는 평균 간격(초). `0`이면 안 들어옴 |
| `depths` | – | `1`이면 등장 깊이 보정 화면. 아래 "새 기록 등장" 참고 |

전시장에서는 `?glass=...`로 유리 단계를 **박아두는 걸 권합니다**. 워치독은 안전장치이지
매번 같은 판단을 한다는 보장이 없어서, 실기기에서 한 번 재보고 고정하는 쪽이 예측 가능합니다.

## Vercel 배포 — 기존 도메인은 그대로 두고 새 도메인 하나

브랜치는 **`main` 하나**입니다. 온보딩 씬과 지도가 같은 레포·같은 브랜치에 살고,
**Vercel 프로젝트를 둘로 나눠서** 서로 다른 도메인으로 나갑니다.

| 프로젝트 | Root Directory | 나가는 주소 | 내용 |
|---|---|---|---|
| 기존 (그대로 둠) | 레포 루트 | 원래 도메인 | 온보딩 씬 (`index.html`) |
| 새로 만듦 | `statistics` | 새 도메인 | 머무름의 지도 |

**레포 루트에는 `vercel.json`을 두지 않습니다.** 루트에 두면 기존 프로젝트의 동작까지
같이 바뀝니다. 설정은 `statistics/vercel.json` 안에만 있고, Root Directory를
`statistics`로 잡은 프로젝트만 그 파일을 읽습니다.

### 새 프로젝트 만들기

1. Vercel → **Add New… → Project** → 같은 레포(`survey_boat`) 선택
2. **Root Directory** 의 **Edit** → `statistics` 선택
3. **Framework Preset** → `Other`, Build Command·Install Command는 **비워 둡니다**
   (정적 파일이라 빌드가 없습니다)
4. **Deploy** → `프로젝트이름.vercel.app` 주소가 바로 생깁니다
5. **Settings → Domains** → **Add** → 새 도메인 입력 → Vercel이 알려주는 A/CNAME 레코드를
   도메인 산 곳(가비아·Cloudflare 등)의 DNS에 입력

Production Branch는 기본값 `main` 그대로 두면 됩니다.

> **404가 뜬다면** Root Directory가 `statistics`로 잡혔는지 먼저 보세요.
> `프로젝트.vercel.app/js/main.js` 가 200이면 파일은 올라간 것이고,
> 그것도 404면 Root Directory 설정 문제입니다.

### GLB 사본에 대해

Vercel의 Root Directory는 **그 폴더 밖의 파일을 배포에 포함하지 않습니다.** 그래서
`statistics/assets/Scene.glb`에 루트 것의 사본을 뒀습니다. 코드는 후보 두 개를 순서대로
시도하므로(`config.js`의 `MODEL_URLS`) 어느 형태로 올리든 그대로 돕니다.

| 배포 형태 | 실제로 쓰이는 경로 |
|---|---|
| Vercel, Root Directory = `statistics` | `./assets/Scene.glb` |
| 레포 루트 서빙 (로컬 서버, GitHub Pages) | `./assets/Scene.glb` (없으면 `../assets/Scene.glb`) |

사본은 드리프트 위험입니다 — 블렌더에서 모델을 다시 굽고 루트만 갈아끼우면 온보딩의
배와 지도의 배가 소리 없이 달라집니다. **모델을 다시 구우면 반드시:**

```bash
node statistics/tools/sync-model.mjs          # 맞춘다
node statistics/tools/sync-model.mjs --check  # 다른지만 확인 (다르면 exit 1)
```

### 배포 전에 한 번 볼 것

- **three.js를 unpkg CDN에서 받습니다.** unpkg가 죽으면 화면도 죽습니다. 전시 당일
  리스크를 없애려면 `three.module.js`와 `GLTFLoader.js`를 레포에 넣고 importmap을
  그쪽으로 돌리는 게 안전합니다(약 1.4MB). 지금은 온보딩 씬과 같은 방식을 유지했습니다.
- **캐시**: `statistics/vercel.json`이 `assets/` 만 1년 immutable로 잡습니다.
  HTML·JS·CSS는 Vercel 기본값이라 전시 중 코드를 고치면 새로고침으로 반영됩니다.

## 온보딩 씬과 공유하는 것 — `shared/`

두 화면은 같은 바다·같은 배·같은 분류값을 쓴다. 예전에는 각자 자기 파일에 같은 표를
옮겨 적어 두고 있었고, **한쪽만 고치면 소리 없이 갈라졌다.** 지금은 원본이 `shared/`
안에 하나뿐이고 양쪽이 거기서 읽는다.

| 파일 | 담긴 것 | 읽는 쪽 |
|---|---|---|
| `ocean-core.js` | Gerstner 파도 표, 셰이더 GLSL, `waveHeightAt`, `WAVE_WRAP_DOMAIN` | 루트 모듈 / `js/ocean.js` |
| `palette.js` | `TIME_OF_DAY`, `INITIAL_TIME_KEY`, 밝기, `REGION_SAND` | 루트 모듈 / `js/config.js` |
| `ship-tokens.js` | `SHIP_FORWARD_OFFSET`, `SHIP_DRAFT` | 루트 모듈 / `js/fleet.js` |
| `glb-nodes.js` | GLB 노드 이름, `KEYWORD_NODES`(키워드 → 요소), `SIDE_PROPS`, `CLOVER` | 루트 모듈 / `js/fleet.js`·`js/clover.js` |
| `look-tokens.js` | `SCENE_LOOK`(조명 비율·거칠기 상한), `HEMI`(반구광), `AO`, `SURFACE_FX`(광택·테두리·면 변주), `TILT_SHIFT` | 루트 모듈 / `js/main.js`·`js/fleet.js` |
| `boat-look.js` | `BOAT_PAINT`(배 칠 색), `TUBE_TINT`, `LAMP`, 부품 판정 `markHullParts`·`lampTwinZ` | 루트 모듈 / `js/boat-paint.js` |
| `tokens.css` | UI 색, `--scene-grade`, `--scene-vignette` | 두 `index.html` |
| `deps.js` | three 버전 | 루트 모듈 / `js/selfcheck.js` |
| `survey-taxonomy.js` | `REGIONS`, `STATES`, `KEYWORDS` — **바꾸면 보안 규칙 재생성·배포** | 루트 설문 UI / `js/config.js` |
| `record-schema.js` | `RECORD_SCHEMA` — 필드·80자·키워드 2개·검사·`safeImage` | 루트 설문 UI(`ui/record-sync.js`) / `js/store.js` / `../firebase/build-rules.mjs` |
| `db-config.js` | Firebase 웹 설정값 · SDK 버전 · 컬렉션 이름 · `dbMode()` | `ui/record-sync.js` / `record-store.js` / `js/store.js` |
| `record-store.js` | Firestore 어댑터 (구독 · 최신 n건 · 개수 · 쓰기 · 썸네일) | `ui/record-sync.js` / `js/store.js` |

**파도는 표 하나에서 GLSL과 JS가 같이 생성됩니다.** 정점 셰이더의 `gerstnerSum`은
`GERSTNER_WAVES` 표에서 문자열로 만들어지고, 배가 들썩일 높이를 재는 `waveHeightAt`도
같은 표를 돈다. 예전에는 이 둘을 손으로 맞춰야 했고(한 글자만 어긋나도 배가 수면에서
뜨거나 잠긴다), 심지어 화면마다 두 벌씩 있었다. 이제 표만 고치면 넷이 같이 따라온다.

**확인된 동작**: `shared/ocean-core.js`의 파장을 2.2 → 3.7로, `shared/palette.js`의
바다색을 `#2fb3e6` → `#ff00aa`로 바꿔 봤더니 **두 화면의 셰이더·파고·색이 모두** 따라왔다.

### 왜 `shared/` 가 `statistics/` 안에 있나

지도는 Vercel에서 Root Directory를 `statistics`로 잡아 따로 배포된다. Vercel은 **그 폴더
밖의 파일을 배포에 포함하지 않으므로**, 공유 파일이 레포 루트에 있으면 지도 배포에서
404가 난다. 그래서 공유 코드는 `statistics/` 안에 두고 루트의 온보딩 씬이
`./statistics/shared/`로 가져다 쓴다. **위치가 이상해 보여도 옮기지 말 것** — 옮기는
순간 지도 배포가 깨진다.

### 루트 `index.html`은 읽기만 한다

`shared/`가 여기 있다 보니 루트의 온보딩 씬이 이 폴더를 `import` 한다. 방향이 거꾸로
보이지만 **그렇다고 지도 쪽에서 루트를 고치라는 뜻이 아니다.** 설문 페이지는 설문
세션의 것이다. 이 폴더에서 루트로 나가는 쓰기는 없다 — 읽기만 한다.

| | 누가 고치나 |
|---|---|
| `../index.html`, `../assets/` | 설문 세션만 |
| `statistics/` 전체 (`shared/` 포함) | 지도 세션 |

설문 쪽에서 지역·키워드·팔레트를 바꿔야 하면 `../index.html`에 표를 다시 적지 말고
**`shared/` 안의 파일을 고친다.** 그래야 두 화면이 같이 따라온다.

**루트 파일을 통째로 읽지 말 것.** `../index.html`은 3,000줄이 넘어서 한 번 여는 것만으로
세션 예산의 상당 부분이 날아간다. 필요한 줄만 집는다.

```bash
git log --oneline -- ../index.html | head -3   # 설문이 바뀌었나
grep -n 'MODEL_URL' ../index.html              # 값 하나만
sed -n '985,995p' ../index.html                # 앞뒤 맥락만
```

### `survey-taxonomy.js` 만 클래식 스크립트인 이유

이 값들을 쓰는 온보딩의 설문 UI는 클래식 `<script>` 안에 있고(인라인 `onclick` 핸들러가
전역을 참조해서 모듈로 바꿀 수 없다), 클래식 스크립트는 `import`를 못 쓴다. 그래서
전역에 얹는 방식으로 두 쪽 다 읽게 했다. 두 HTML 모두 모듈보다 **앞에** 이 파일을
`<script src>`로 넣어 둔다 (모듈은 defer라 먼저 나온 클래식 스크립트가 항상 먼저 실행된다).

### 아직 공유 안 되는 것

`Scene.glb` 는 파일이라 import로 묶을 수 없다. `statistics/assets/`에 사본이 있고
`sync-model.mjs`로 맞춘다 (아래 "GLB 사본에 대해" 참고).

### 흐름 — 배는 어떻게 움직이나

배는 **전부 같은 방향으로, 같은 속도로** 흐릅니다. 화면 왼쪽 끝에서 나타나 오른쪽으로
빠지고, 띠 폭(`FLOW_CORRIDOR_W` = 30)을 다 지나면 반대편 끝으로 감겨 다시 들어옵니다.
띠 폭은 상수가 아니라 화면비(`FLOW_ASPECT_MAX` = 9:16)에서 가장 먼 배(깊이 44)의 화면 반폭에 여유 3을 더해 역산합니다.

**[10-03] 화면은 9:16 하나다.** `#stage`(css/panel.css)가 창 안에서 가장 큰 9:16 상자로 가운데 서고 남는 곳은
어둡게 비운다 — 가로 모니터에서 띄워도 전시 화면과 같은 그림이다. 예전엔 16:9 가로 화면까지 받느라 띠가 86이라
세로 화면에서는 배의 2/3가 화면 밖을 돌았다(사용자: "더 빽빽하게"). 9:16으로 역산하고 깊이 띠도 12~44로 좁히고
간격을 2.7로 줄여(`FLEET_MIN_GAP`), 같은 배가 화면 가운데 바다에 모인다.

속도는 상수로 박지 않고 **"기준 깊이의 배가 40초에 화면을 건넌다"**로 정의하고
카메라 화각에서 역산합니다(`FLOW_CROSS_SEC`, `FLOW_REF_DEPTH`). 화면 폭은 기기
화면비마다 다르기 때문입니다. 세로 화면(1080×1920) 실측:

| 카메라 앞 거리 | 화면 가로 폭 | 횡단 시간 |
|---|---|---|
| 10 (화면 아래끝) | 6.5 | 24초 |
| 15 | 8.6 | 32초 |
| **20 (기준)** | **10.9** | **40초** |
| 30 (화면 세로 중앙) | 15.7 | 58초 |
| 48 (가장 먼 배) | 24.6 | 90초 |

속도를 하나로 통일한 게 핵심입니다. **깊이마다 속도를 달리 주면 원근이 사라져
평면 스크롤처럼 보입니다.** 가까운 배가 빨리, 먼 배가 천천히 지나가는 게 깊이감입니다.
띠 폭이 화면보다 넉넉해서 감기는 순간은 언제나 화면 밖이고, `selfcheck.js`가 이걸
화면비마다 검산합니다.

한 번에 화면에 보이는 배는 80척 중 절반 남짓입니다(10-03 이전엔 약 12척). 나머지는 띠의 화면 밖 구간에 있고,
약 5분 주기로 다시 들어옵니다. 21:9 같은 더 넓은 화면에 걸려면 `FLOW_ASPECT_MAX`를 올리면 띠가
따라 넓어집니다 — 대신 같은 80척이 더 긴 띠에 퍼져 화면 속 배가 그만큼 줍니다.

### 실제 공간과 카메라 — 바다·하늘·빛은 월드에, 카메라는 그 밖에

바다·하늘·조명·배는 실제 공간처럼 월드에 고정돼 있고, 카메라는 그 공간 밖에 따로 선
촬영 장비입니다. **카메라는 한 자리(원점, 높이 8)에 서서 고개를 돌리고 렌즈를 당길 뿐**
수면 위를 날아다니지 않습니다.

예전에는 셋 다 이 원칙을 어겨서 줌 인·아웃 때 "바다가 배보다 더 움직이고, 빛이 바다 면과
따로 논다"로 보였습니다.

| 예전 | 그래서 보이던 것 | 지금 |
|---|---|---|
| 바다 판이 매 프레임 카메라 발밑으로 옮겨 다녔다 | 파도 높이는 월드 좌표였지만 그걸 재는 **정점**이 카메라와 함께 미끄러져, 삼각형 면이 매 프레임 다른 자리에서 다시 만들어졌다. 플랫 셰이딩이라 면마다 빛이 달라져 번쩍였다 | 바다는 **월드에 고정된 한 장**. 면도, 면이 받는 빛도 제자리 (`ocean.js` `buildWater`) |
| 카메라가 배 앞 11까지 수면 위를 날아갔다(돌리) | 시차 — 가까운 바다는 빨리, 먼 배는 느리게 지나감 | **제자리에서 고개 돌리기 + 줌.** 시차가 없어 화면 전체가 한 장의 사진처럼 같이 커진다 |
| 하늘 그라디언트를 화면 배경에 칠했다 | 고개를 돌려도 하늘은 화면에 붙어 있고 수평선만 움직임 | 하늘도 월드의 돔. 색은 "그 방향이 수평선에서 몇 도 위인가"로 정한다 (`sky.js` `makeSkyDome`) |

**바다 격자는 칸 크기가 곳곳이 다릅니다.** 줌이 당겨 보는 구역(카메라 앞 8~46, 좌우 ±16)은
칸 0.32로 촘촘하고, 멀어질수록 넓혀 먼 바다는 2.6까지. 예전 균일한 0.83 칸이었다면 3배 줌에서
삼각형 하나가 화면 폭의 3분의 1을 차지합니다. 원근 때문에 먼 칸은 작게 보이므로 화면에서의 면
크기는 오히려 고르게 됩니다. 정점 수는 예전과 같은 5만 남짓입니다(`config.js` `WATER_*`).

**바다 결 — 반복 무늬 끊기 (10-01, `js/sea-variety.js`, `config.js` `SEA_VARIETY`).** 파도는 짧은 Gerstner
셋(파장 2.2/1.3/0.8)뿐이라, 깊이 150을 한 화면에 담는 지도에서는 같은 물결이 수백 번 되풀이돼 벽지 같은
빗금이 보였고, 줌 구역 밖 큰 칸에서는 파도를 건너뛰어 찍어 면이 들쭉날쭉했습니다. 파도 표는 설문과 같이
쓰므로 그대로 두고, 지도에서만 파도마다 진폭에 배수를 곱합니다.

| 무엇 | 어떻게 |
|---|---|
| 멀리서 물결 줄이기 | 카메라에서 28~64 사이에서 물결을 15%까지 — 먼 바다는 하늘 반사·반짝임으로 읽힌다. 도착 제시 구역(13~33)은 그대로 |
| 큰 칸에서 줄이기 | 칸이 파장의 0.4~0.8배를 넘는 곳에서 그 파도를 15%까지 — 면이 들쭉날쭉하지 않게 |
| 물결 센 곳/잔잔한 곳 | 길이 23·37·61의 긴 사인 셋을 섞은 진폭 배수(0.45~1.3), 천천히 흐른다 — 보이는 범위에서 되풀이되지 않는다 |

배수는 물 셰이더(GLSL)와 배 들썩임(JS, `ocean.js` `seaHeightAt`)이 같은 식을 쓴다 — 어긋나면 배가 수면에서
뜨거나 잠긴다. 공유 파일에는 진폭 배수를 꽂는 자리만 생겼고(`makeGerstnerGLSL(gain)`, `waveHeightAt(…, gain)`),
배수가 없을 때의 셰이더 소스는 예전과 글자까지 같다(설문 selfCheck 가 문자열로 검사한다).

**풍경 — 등대 섬·먼 해안·구름·해와 윤슬 (10-03, 사용자: "풍경이 안 예쁘다").** 끝없는 평면 바다와 그라디언트 하늘뿐이라
눈이 머물 곳이 없었다. 지도 전용으로 넣은 것(값은 `config.js` `LANDMARK` · `SKY_LOOK`):

| 무엇 | 어떻게 | 비용 |
|---|---|---|
| 등대 섬 | 설문 GLB의 섬 바위·오두막·등대를 먼 바다(깊이 84, 화면 왼쪽 가운데)에 하나. 등대 밑엔 바위를 하나 더 깔았다(지금 GLB엔 설문의 뒷산이 없다). 밤·저녁엔 등대 창이 켜진다(`landmarks.js`) | 재질별로 구워 draw call 3 |

### 새 기록 등장 — 제자리 줌

배는 자기 자리에 생겨서 그대로 있고, 카메라가 그쪽으로 고개를 돌려 렌즈를 당깁니다.

| | 국면 | 일어나는 일 |
|---|---|---|
| 1 | `approach` | 고개를 돌리며 줌(`ARRIVAL_ZOOM_SEC` 3.2초). 배는 아직 안 보인다 |
| 2 | | 줌이 끝나기 `ARRIVAL_APPEAR_LEAD`(0.3초) 전에 배가 나타난다 |
| 3 | `hold` | 화면 아래에 방금 도착한 문장을 띄우고 `ARRIVAL_HOLD_SEC`(8초) 머문다. **배는 흐르지 않는다** |
| 4 | `return` | 카드를 내리고 줌을 푼다. **배는 이때부터 흐르기 시작한다** |

**줌 배율 = 예전 제시 화면보다 배가 3배 크게**(`ARRIVAL_ZOOM`). 예전 화면은 배에서 거리
13.6(= hypot(11, 8))에 화각 50도였습니다. 배가 화면에서 차지하는 크기는 거리 × tan(화각/2)에
반비례하므로, 배까지 거리로 화각을 정합니다 — 가까운 배(13)는 16도, 먼 배(33)는 7도 남짓의
망원입니다. 배는 화면 가운데보다 조금 위(42%)에 앉습니다. 아래에 방금 도착한 문장이 뜹니다.

**고개와 렌즈를 같은 속도로 섞지 않습니다.** 고개는 앞 75% 안에 다 돌리고 렌즈는 15%부터
당깁니다. 둘을 똑같이 섞으면 중간쯤 화각이 좁아지는 속도가 시선이 따라가는 속도보다 빨라,
배가 화면 가장자리 밖으로 잠깐 빠졌다 돌아옵니다. 풀 때는 같은 곡선을 거꾸로 밟아 렌즈가
먼저 풀리고 고개가 나중에 돌아옵니다(`camera.js` `setZoomProgress`). 렌즈는 배율이 고르게
변하도록 tan(화각/2)의 로그로 섞습니다.

배 크기 배수(`ARRIVAL_SCALE`)는 **1.0**입니다 — 크게 보이는 건 렌즈의 일이지 배를 부풀릴
일이 아닙니다.

**등장 자리 — 화면 왼쪽 절반에서만.** 배는 화면 오른쪽으로 흐르므로, 오른쪽에서 등장하면
줌이 풀리자마자 화면 밖으로 빠집니다. `ARRIVAL_X_MIN/MAX`(0.10~0.88)는 그 깊이에서의 화면
**한가운데(0)에서 왼쪽 끝(1) 사이 비율**입니다.

**깊이는 `ARRIVAL_DEPTH_MIN/MAX`(13~33) 사이 무작위** — 09-26에 고른 "너무 멀지 않게"입니다.
그때는 위 44%를 덮던 패널 뒤에 가려지지 않는 한계였고, 패널을 걷은 지금은 줌 배율과 묶입니다
(멀수록 더 좁은 망원이 필요합니다). 값을 눈으로 정하려면:

```
http://localhost:8000/statistics/?depths=1
```

주요 깊이마다 배를 한 척씩 **같은 화면 가로 위치**에 놓고 숫자를 붙여 줍니다. 세로 화면
(FOV 50, 카메라 높이 8, 시선 39) 실측:

| 깊이 | 10 | 14 | 18 | 22 | 26 | 32 | 40 | 48 |
|---|---|---|---|---|---|---|---|---|
| 화면 세로 위치 | 화면 아래 | 85% | 73% | 66% | 60% | 55% | 49% | 46% |

**[10-03] 등장 자리는 넉넉하게 — 줌 화면에 이웃이 겹치지 않게.** 배가 촘촘해지자 3배 줌 화면에 앞뒤 배가 주인공 배와
겹쳐 잡혔다. 9:16 줌 화면은 옆으로는 ±1.2뿐이지만 내려다보는 각도라 앞뒤로 깊이 ±5.7이 들어온다. 그래서 등장 자리는
옆 2.8 · 앞뒤 5.5의 타원 안이 비어 있는 곳을 찾고(`ARRIVAL_CLEAR`), 보여주는 동안 나머지 배의 흐름을 15%로 늦춰
(`ARRIVAL_FLOW_MUL`) 이웃이 화면을 쓸고 지나가지 않게 했다. 그래서 이 배의 격자 좌표는 다시 흐르기 시작하는 순간에 정한다.

**자리를 푸아송 격자에서 고르지 않는 이유.** 화면에 보이는 바다는 띠(예전 88) 중 10 남짓이고
그중 왼쪽 절반이면 4 정도입니다. 115개 자리 가운데 그 창에 들어와 있는 건 한순간에
서너 개뿐이라, 그것들이 이미 차 있으면 조건을 만족하는 빈 자리가 **아예 없습니다**.
실제로 그래서 배가 화면 밖 깊이 43에 등장하고 카메라가 28 단위를 날아갔습니다.
지금은 조건을 먼저 만족시켜 놓고 겹침을 직접 잽니다(`main.js`의 `_pickArrivalSpot`).

**얼어 있는 동안의 격자.** 제시하는 동안 이 배만 멈춰 있고 나머지는 (늦춰진 속도로) 계속 흐릅니다.
예전엔 그만큼 밀릴 격자를 미리 역산했고, 지금은 다시 흐르기 시작하는 순간의 흐름 거리로 격자 좌표를 정합니다. 그래서 다시 흐르기 시작하는 순간 배가 정확히 제자리에
얹히고, 이웃과의 간격이 한 번도 깨지지 않습니다. (실측 어긋남 0.01 이하)

**줄은 배가 아니라 기록으로 섭니다.** 관람객이 몰려 제출이 연출보다 빨리 들어오면
줄이 서는데, 예전에는 배를 먼저 바다에 놓고 줄을 세웠습니다. 그러면 차례를 기다리는
동안 배가 흘러가 버려서 위의 역산이 통째로 어긋나고, 줄에서 밀려난 배까지 전부 화면
왼쪽의 좁은 창에 놓여 서로 겹쳤습니다(실측 간격 0.08). 지금은 차례가 왔을 때 배를
만들고, 줄에서 밀려난 기록은 연출 없이 푸아송 격자에 놓습니다.

### 표현 채널 — 키워드는 확정, 나머지는 난수

**키워드 → 배에 나타나는 요소는 확정됐습니다**(설문과 같은 매핑). 그래서 요소는
`STYLE_SOURCE`와 상관없이 **늘 실제 답변에서** 옵니다 — 난수로 뽑으면 통계 패널에는
"가족"이 가장 많다고 뜨는데 바다에 튜브가 드문, 서로 어긋난 화면이 됩니다.

아직 정해지지 않은 채널(지역 → 선체 색조)만 난수에서 뽑습니다. `config.js`의 한 줄로 바뀝니다:

```js
export const STYLE_SOURCE = "random";   // "random" | "record"
```

난수는 `record_id`를 시드로 한 **고정 난수**입니다 — 매 프레임 새로 뽑으면 색이 깜빡이고,
매 로드마다 새로 뽑으면 전시 중 재시작할 때 바다가 통째로 달라집니다. 지금 방식이면
"그 기록의 배"는 언제 봐도 같은 배입니다.

**중요**: 난수인 건 **배의 모습뿐**입니다. 제목 카드의 누적 수와 통계(키워드·상태·지역
분포)는 지금도 실제 기록에서 집계합니다.

| 채널 | 어떻게 | 비용 |
|---|---|---|
| 키워드 → 요소 | 공구함·램프·튜브·고양이·서핑보드·클로버·갈매기·종·의자+컵·이젤+의자. 요소마다 InstancedMesh 하나, **그 요소를 단 배에만** 인스턴스 | 쓰이는 요소 하나당 draw call +1 |
| 선체 색조 | `instanceColor` (GLB 원본 색에 흰색 근처 색조를 곱함 — 원본 색을 안 버림) — **미확정, 지금 난수** | 공짜 |

**캐빈 색은 채널이 아닙니다.** 키워드는 배에 나타나는 요소로만 표현한다는 것이 사용자
결정이고(설문과 같은 규칙), 캐빈은 모든 배가 설문 배와 같은 크림 페인트를 입습니다
(`boat-paint.js` — 아래 "설문 배 모습").

매핑을 바꾸거나 채널을 늘릴 때 손대는 파일은 **`style.js` 하나**입니다. 새 채널에
인스턴스 컬러를 걸려면 `fleet.js`의 `TINT_ROLES`에 한 줄만 더하면 됩니다.
씬·카메라·패널 코드는 "배마다 style 객체 하나"만 알고, 그 안이 어떻게 정해졌는지는
모릅니다.

### 상태별 자리·움직임은 어디 갔나

처음 판에는 상태(머무르는 중 / 떠날 준비 중 / 오가는 중 / 돌아온 사람 / 아직 모르겠음)에
따라 바다 중심에서의 거리와 움직임이 달랐습니다. 채널 구성이 아직 변동될 수 있다고 해서
**흐름 하나로 단순화하고 잠시 뺐습니다.** 되살릴 자리는 `motion.js`의 `stepBoat` 한 곳이고,
깊이나 속도 배수를 `style.js`가 정하게 하는 방법도 있습니다.

## 배의 요소와 룩 — 설문과 맞춘 것 (2026-09-27)

설문 세션이 모델을 새로 굽고 룩을 고정한 뒤 넘긴 인수인계(`../HANDOFF-map.md`)를 반영했다.
원칙은 그 문서 1장 그대로다 — **두 화면이 똑같아야 하는 "값"은 `shared/`에서 읽고,
"코드"(셰이더·렌더 설정)는 화면마다 따로 쓴다.** 설문 `index.html`에서 숫자를 베껴 오지 않는다.

### 키워드 → 배의 요소

| 키워드 | 요소 | | 키워드 | 요소 |
|---|---|---|---|---|
| 일 | 공구함 | | 우연 | 클로버 (코드로 선체에 투영) |
| 관계 | 램프 | | 자유 | 갈매기 |
| 가족 | 튜브 | | 불안 | 종 |
| 주거 | 고양이 | | 익숙함 | 의자 + 컵 |
| 소속감 | 서핑보드 | | 창작 | 이젤 + 이젤 의자 |

매핑은 `shared/glb-nodes.js`의 `KEYWORD_NODES` 하나에서 온다. 설문도 같은 표를 읽는다.

**요소 하나 = InstancedMesh 하나 = draw call 하나.** 배가 80척이든 800척이든, 요소 종류
수만큼만 늘어난다. 새 GLB의 요소 11개는 전부 재질 한 조각(`Atlas_Lit`)이라 정확히 1씩이다.

**그 요소를 단 배에만 인스턴스를 둔다.** 예전에는 소품마다 인스턴스를 배 수만큼 깔아 두고,
그 소품이 없는 배 자리는 크기 0 행렬로 뭉개서 지웠다. 소품이 둘일 때는 괜찮았지만
열한 개가 되면 정점 셰이더가 안 보이는 소품까지 다 돈다 — 요소 삼각형 합계 6,894 × 80척
≈ 55만 개를 매 프레임 헛돈다. 지금은 요소마다 인스턴스 목록을 따로 두고 그 키워드를
가진 배만 채운다. 결과적으로 요소를 12종 붙였는데도 화면 전체 삼각형이 줄었다
(264,226 → 211,140). 아무 배도 안 쓰는 요소는 count 0이라 draw call 자체가 없다.

**뱃전 요소는 카메라 쪽으로.** 서핑보드·종·튜브·고양이·클로버(`SIDE_PROPS`)는 뱃전에 붙어 있어서
카메라 반대쪽에 있으면 선체에 가려진다. 설문은 드래그로 둘러보므로 카메라 쪽이 바뀔 때마다
거울상 자리로 옮긴다. 지도는 모든 배가 같은 방향으로 흘러 카메라가 늘 같은 뱃전(우현)을
보므로 **로드할 때 한 번만** 정해 지오메트리에 구워 넣는다. InstancedMesh는 인스턴스 행렬의
행렬식을 안 보기 때문에(음수 배율로 뒤집으면 면이 안쪽을 본다) 지오메트리를 직접 뒤집고
삼각형 감김 방향도 바꾼다. 지금 GLB에서는 튜브만 옮겨졌다. 흐름 방향(`FLOW_DIR`)을 뒤집으면
카메라 쪽 뱃전도 저절로 바뀐다.

**클로버**는 GLB에 없다. 설문과 같은 방식(선체 표면에 `DecalGeometry`로 투영)으로 만들되,
지도는 배를 배율 1로 구워 두므로 `CLOVER`의 값(설문 월드 단위, 배율 3.38 기준)을
`refScale`로 나눠 쓴다. 늘 카메라 쪽 뱃전에 만든다.

> **클로버와 작은 요소들은 멀리서 거의 안 보인다.** 배와의 비율이 설문과 같아서, 흐름 중인
> 배에서는 점이고 등장 연출(카메라가 배 앞 11까지 갈 때)에서 겨우 알아볼 정도다. 두 화면이
> 같은 작품으로 보이게 하려고 크기를 설문과 맞춰 뒀다. 지도에서만 키우려면 `clover.js`에서
> `CLOVER.size`에 배수를 곱하면 된다.

**캐빈 색은 없앴다.** 사용자 결정 — 키워드는 요소로만 나타낸다. 캐빈은 GLB의 크림색
재질 그대로다(09-30부터는 설문과 같은 페인트 — 아래 "설문 배 모습"). 지도만 쓰던 `KEYWORD_COLOR`·`KEYWORD_PROP`·`CABIN_BASE_COLOR`는
`shared/`에서 지웠다(설문은 셋 다 안 읽는다 — 지우기 전에 확인했다).

주변광 0.22 `#ffffff`, 해 1.7325 `#fff7e2`, 테두리광 0.33 `#bfe7ef`, 반구광 0.792
하늘 `#b0d1da`·바닥 `#2083a9`. 설문에만 있는 Spot은 등대 불빛이라 가져오지 않았다.

`sunPos`를 그대로 쓰면 지도에서만 해가 배 뒤로 가 카메라 쪽 옆면이 전부 그늘이었다(선체·마스트·캐빈이
설문 실측의 0.6~0.7배). 해·테두리광의 z를 뒤집어 두 화면이 배를 같은 쪽 빛으로 찍는다(`main.js`).
물은 이 조명을 안 받고 반짝임 방향을 따로 가져서(`ocean.js` `uSunDirection`) 그대로다.

**구운 AO도 넣었다** (`look-tokens.js` `AO`, 설문과 같은 식·같은 세기). 인수인계에서는
"멀리서는 효과가 작으니 선택"이었는데, 켜고 끈 근접 장면을 나란히 비교해 보니 고물 쪽
우묵한 곳·캐빈 밑동·요소가 갑판에 닿는 자리에 그늘이 들어가 배가 덜 납작해 보였다.
값은 굽기 단계에서 GLB의 모든 메쉬에 정점 속성으로 이미 들어 있어서(`_ao`) 늘어나는 건
픽셀당 곱셈 몇 번뿐이다 — draw call도 텍스처도 그대로다. 클로버는 GLB 밖에서 만든
지오메트리라 `_ao`가 없고, 그래서 패치하지 않는다(`fleet.js` `patchBakedAO`).

**표면 효과·틸트시프트도 넣었다** (09-30 사용자 결정, `../HANDOFF-map.md` 19장). 처음엔 "가까이서 한 척"
전용이라 뺐던 것들이다. 걱정했던 것은 이렇게 풀었다:
- 멀리 작은 배에서 테두리 빛이 번쩍이는 점이 되는 것 → 배가 화면에서 130px보다 작아지면 광택·테두리를 줄이고
  45px 아래에선 끈다(`surface-fx.js` `FAR_FADE`). 도착 제시(약 620px)와 가까운 배(약 150px)는 설문과 같은 세기.
- 면 색 변주가 파도에 기울 때마다 깜빡이는 것 → 해시를 인스턴스 행렬 전(물체 공간) 면 법선으로 낸다.
- 틸트시프트 비용 → CSS `backdrop-filter` 띠(재 보니 WebGL 두 패스보다 쌌다), 프레임이 모자라면 워치독이 가장 먼저 끈다.
- 구운 AO를 두 번 곱하지 않게 AO 패치와 표면 효과 패치를 나눴다(`material-patch.js`로 겹쳐 건다).

**여전히 안 가져온 것** — 부드러운 그림자(사용자 결정, 지도는 그림자 패스가 없다).

- **칠은 인스턴스 색조보다 먼저 들어간다**(`map_fragment` 뒤). 배마다 다른 선체 색조가 갑판·마스트에도 옅게 남아
  한 배의 선체와 갑판이 서로 다른 배처럼 보이지 않는다.
- **좌표 부호.** 지도는 뱃머리 보정 회전까지 구워서 뱃머리가 +X다(설문 코드는 −X). 캐빈 뱃머리 쪽 창 넷은
  +X 면, 옆면은 창이 뱃머리 쪽·문이 선미 쪽이 되게 가로를 뒤집었다.
- **색은 `BOAT_PAINT`를 그대로 쓰고, 지도에서 다르게 찍히는 것만 `config.js` `MAP_PAINT_GAIN`으로 맞춘다.**
  지금은 갑판 하나(레퍼런스 `#845044`에 맞춤). `BOAT_PAINT`를 고치면 설문 배가 바뀐다.
- **뺀 것:** 램프 흔들림과 밤 램프 불빛(사용자 결정), 램프 조명·수면 반사(80척이면 조명 80개).
- `selfcheck.js`가 부품 개수·갑판 비율·램프 자리를 확인한다 — GLB를 다시 뽑으면 조용히 틀어지는 종류다.

### 결론을 틀리게 내지 않기 위한 규칙 (`insights.js`)

결론 문장은 데이터에서 자동으로 만들어져 전시장에 그대로 뜹니다. 숫자·방향·조사가
틀리면 관람객이 그대로 읽습니다. `node statistics/tools/check-insights.mjs` 가 아래를 전부
검사합니다(38개).

- **키워드는 상태마다 다른 질문의 답입니다.** 설문 Q3은 상태에 따라 "머무르게 / 떠나게 /
  오가게 / 망설이게 하는 것"을 묻습니다. 그래서 **"사람들이 여기 머무는 건 ○○ 때문"은
  머무는 사람(머무르는 중·돌아온 사람)의 답만 셉니다.** 예전 화면은 전부 합쳐 세어서,
  떠나는 사람의 '일'까지 머무는 이유로 둔갑할 수 있었습니다. 묶음은 설문 질문 문구가 같은
  상태끼리 자동으로 만듭니다(`MOTIVES`) — 설문이 문구를 바꿔도 여기를 고칠 필요가 없습니다.
- **표본이 적으면 말하지 않습니다** — 문장 5개 미만이면 "아직 이릅니다". 지역·동기 묶음은
  3개 미만이면 비교에서 뺍니다(차트에는 옅게 남습니다).
- **1위가 동률이면 둘 다 말합니다.** "가장 붐빈 때"도 한 칸이 혼자 높을 때만 말합니다.
- **분모를 밝힙니다.** 키워드는 한 문장이 두 개까지 골라 "표"와 "사람"이 다릅니다.
- **지역색은 리프트로 말합니다** — "천안은 ‘오가는 중’이 평균보다 1.7배 많습니다".
  칸 3개·지역 5명 미만, 1.3배 미만은 말하지 않고, '비공개'는 지역이 아니라 뺍니다.
- **짝은 조건부 비율로 말합니다** — "‘일’을 고른 사람의 80%가 ‘가족’도 골랐습니다".
- **조사는 받침을 보고 붙입니다**(`text.js`) — 천안은/비공개는, 가족을/자유를, 31%가.

### shape — 지표와 표시 방식을 맞추는 장치

지표는 자기 shape 을 선언하고, 표시 방식은 받을 수 있는 shape 을 선언합니다. `index.js`가
짝을 지을 때 맞는지(해석 함수가 있는지도) 검사하므로, 안 맞는 조합은 **켜는 순간 콘솔에서** 걸립니다.

| shape | 구조 | 이 shape 을 받는 표시 방식 |
|---|---|---|
| `rows` | `{items:[{label,count,share}], total, n}` | `bubble` · `ranking` · `bars` · `headline` |
| `groups` | `{groups:[{key,label,n,items}]}` | `motives` |
| `matrix` | `{rows, cols, cells, rowTotals, colTotals, max, total}` | `heatmap` |
| `pairs` | `{nodes, links, maxLink, freq}` | `network` |
| `scores` | `{items:[{label,score,n}], min, max}` | `thermo` |
| `pulse` | `{total, buckets, recent, windowMin, lastAgoMin}` | `pulse` |
| `stream` | `{items:[{text, meta}]}` | `textwall` |

표시 방식의 계약:

```js
accepts: "rows"                   // 받을 수 있는 shape
render(data, ctx) → HTML 문자열   // ctx.highlight = 결론이 가리키는 것, ctx.aspect = 차트 자리의 가로/세로
legend?(data) → 범례 HTML          // 선택
```

three.js도, 패널의 DOM 구조도, 어떤 지표였는지도 모릅니다. 이 화면 밖으로 옮길 때
**가져갈 것은 `views.js`의 함수 하나와 `css/stats.css`의 같은 이름 블록 하나뿐**입니다.
모든 표시 방식은 자리의 높이를 100% 채우고 글자는 `em`이라, 어떤 크기의 자리에도 들어갑니다.

### 화면의 두 시간 — 풍경과 통계

통계를 크게 보여주려면 화면 한가운데를 내줘야 하고, 그러면 바다가 가려집니다. 그래서 둘을
겹치지 않고 **번갈아** 보냅니다 — 한 편의 필름처럼. 레퍼런스 화면이 개인의 이야기와 통계를
번갈아 보내고 절대 동시에 띄우지 않는 것과 같은 원칙입니다.

| 시간 | 길이 | 화면 |
|---|---|---|
| **풍경** | 30초 (`LANDSCAPE_SEC`, 켜자마자는 8초) | 수평선까지 트인 바다와 흐르는 배들. 위쪽 제목 아래 흰 실선 위로 금색 선이 차오르며 다음 장을 예고한다 — "02 같은 낱말, 다른 이유 · 다음 장" |
| **통계** | 3장 (`SESSION_CHAPTERS`) | 바다가 한 톤 가라앉고(`.stageDim`, 가운데가 더 깊게) 가운데 카드가 떠서 통계를 한 장씩. 다 보여주면 카드가 내려가고 다시 풍경 |

180초 주기와 같습니다.

통계 시간에도 배는 들어옵니다. 방금 제출한 사람은 화면에서 자기 배를 찾습니다 — 이 화면에서
가장 중요한 순간입니다. 그래서 **새 배가 언제나 먼저**이고, 통계는 잃어버리지 않고 밀릴 뿐입니다.

| `return` 줌을 푸는 중 | — | 카드 내림 |
| 끝 | 끊긴 시간으로 복귀 — 통계였다면 카드가 다시 뜨고, 그 장을 절반도 못 봤으면 처음부터, 넘게 봤으면 다음 장. 풍경이었다면 남은 시간만큼 | — |

새 배가 잇달아 들어오면(줄 최대 3척) 그동안 통계는 기다립니다 — 그 시간엔 사람이 곧 통계입니다.

숫자를 배가 보일 때 올리는 이유: 숫자가 먼저 오르고 몇 초 뒤에 배가 오면 관람객에게는 둘이
다른 사건으로 보입니다. 연출 쪽에 무슨 일이 생겨도 40초가 지나면 그냥 셉니다(`panel.js`).

[변경] 한때 새 배가 들어오면 통계 자리에 그 문장을 전체 속에 놓는 "LIVE 장"("이 문장은 ‘일’
때문에 떠나려는 7번째 이야기입니다")을 띄웠습니다. 새 배와 통계를 **데이터로** 잇는 방식이었는데,
의도는 **화면 구성으로** 잇는 것이어서 걷어냈습니다.

**방금 도착한 문장**은 화면 아래 자막입니다(설문의 질문 판과 같은 꼴) — 명조로 그 문장, 그 아래
출발한 곳 · 지금의 자리 · 싣고 온 것 · 기록 시각, 오른쪽 위에 기록 번호 No. 0129. 레퍼런스의
"Drug Facts" 라벨(항목과 값, 초 단위 기록 시각)에서 온 구성이고, 금색 선이 떠 있는 8초에 걸쳐 찹니다.

### 모션

한 장이 들어올 때 **읽는 순서대로 차례로 섭니다** — 굵은 선이 그어지고 → 라벨 → 점선 →
값 → 결론 문장 → 차트의 표식들(순번 `--i` 대로) → 금색 형광 띠 → 각주. 막대는 기준선에서
자라고, 원은 부풀고, 호는 바닥에서 솟고, 히트맵 칸은 대각선으로 번지고, 결론이 가리키는
칸에는 테가 한 번 번집니다. 물러날 때는 위로 살짝 빠지며 흐려지고 선은 오른쪽으로 걷힙니다.
곡선은 레퍼런스의 GSAP `power2.inOut` 근사(`--ease-io`)입니다.

전부 `transform`·`opacity`만 움직입니다 — 유리 카드가 매 프레임 배경을 다시 흐리는 중이라
레이아웃을 흔드는 애니메이션은 쓰지 않습니다. `prefers-reduced-motion`이면 전부 끕니다.

### 정착 온도 — 숫자가 곧 편집 판단인 유일한 지표

다른 지표는 세기만 하지만 이건 해석이 들어갑니다.

| 상태 | 점수 |
|---|---|
| 머무르는 중 | **+2** |
| 돌아온 사람 | **+1** |
| 오가는 중 · 아직 모르겠음 | 0 |
| 떠날 준비 중 | **−2** |

지역별 평균이 "이 지역이 사람을 붙잡고 있는 정도"가 됩니다. 화면에서 뭔가 이상해
보이면 집계 코드가 아니라 `metrics.js`의 `SETTLE_SCORE` 다섯 숫자를 먼저 의심하세요.

### 색을 쓰는 규칙

카드가 어두운 유리라 표식도 어둠 위의 색입니다(dataviz `validate_palette --mode dark`, 카드 바탕 `#151a21`).

- **크기 비교(히트맵)는 한 색상의 밝기 계단 하나**(시퀀셜) — 금색(`--b-gold`)의 알파만 움직인다.
  무지개 램프를 쓰지 않습니다. 진한 칸은 밝아지므로 그 칸 숫자는 짙은 글자(`--b-ink`)입니다.
- **0을 기준으로 갈리는 값(정착 온도)만 따뜻함/차가움 두 색 + 무채색 중앙**(다이버징).
  양극은 `#B8863F`(머무름) ↔ `#4A94CB`(떠남) — 어두운 바탕 검사 전부 통과(ΔE 19.6 · 대비 3:1 이상).
  차가운 쪽을 바다색 계열에서 고른 건 배·바다 은유와 맞물리게 하려는 것입니다.
- **카테고리 색을 돌려 쓰는 표시 방식은 하나도 없습니다.** 이 화면에서 색이 "정체성"을
  나타내는 지표가 없기 때문입니다. **결론이 가리키는 표식만 금색 `--b-gold`, 나머지는 한
  회색 `#62666c`**입니다(강조형). 정상 시각 ΔE 34.6 · 색각 이상 ΔE 32.6 · 둘 다 대비 3:1 이상.
  금색은 밝기가 어두운 모드 권장 띠보다 밝지만, 토큰 값을 그대로 쓰려고 둔 것이고 강조형이라
  "이것 하나"를 가리키는 데만 씁니다.
- **값·라벨 글자는 어둠 위 글자색이고, 색은 그 옆의 표식이 입습니다.** 예외 하나 — 결론 문장의
  강조 낱말은 금색 + 금색 밑줄입니다. 설문에서 고른 낱말을 표시하는 방식 그대로이고, 차트의 금색
  표식과 같은 색이라 문장의 낱말과 그림의 표식이 한눈에 이어집니다(범례 구실).
  (3장 랭킹은 낱말이 곧 표식이라 1위 낱말이 금색입니다.)

### 이 화면에는 hover 가 없습니다

전시장 기기에 입력장치가 없어서(위 결정표) 툴팁을 띄울 방법이 없습니다. 그래서
**모든 값이 화면에 직접 적혀 있습니다** — 히트맵 칸의 숫자, 막대 끝의 %, 온도 축의
점수. 색은 보조일 뿐이고 **색만으로 읽어야 하는 값은 하나도 없습니다.**
(히트맵 칸의 숫자가 곧 표 대체물입니다.)

### 자리 모양에 맞춘 형태

차트 자리의 비율이 화면마다 다릅니다(폰·세로 TV는 2:1 안팎, 가로 모니터는 4:1 가까이).

- 버블 → 가장 큰(결론이 가리키는) 원을 가운데 금색으로 두고, 나머지를 크기순으로 이미 놓인
  원 두 개에 동시에 닿는 자리 중 가운데에서 가장 가까운 곳에 붙인다. 거리를 자리 비율로
  눌러 재서(`ctx.aspect`) 무리가 자리 모양을 닮는다. 예전 패널은 3:1 넘게 납작해서 한 줄로
  늘어놨지만, 가운데 카드에서 한 줄이면 위아래가 빈다.
- 네트워크 → 원 둘레 + 중심 통과선(별 모양으로 엉킴) 대신 **아크 다이어그램**. 호만 늘어나는
  SVG로 그리고 점과 낱말은 HTML로 얹어, 어느 비율에서도 찌그러지거나 비지 않는다.

둘 다 시뮬레이션이 아니라 계산이라, 전시 중 새로고침해도 같은 그림이 나옵니다.

> **[대기] 연령대(`age_bracket`).** 필드가 생기면 이쪽은 `metrics.js`에 한 줄
> (`pick: (r) => r.age_bracket`)이면 끝나고, `heatmap`에 연령대 × 상태로 바로 꽂을 수
> 있습니다. 다만 **필드를 만드는 건 설문 페이지 쪽 일**입니다(분담표 참고).

- **`Scene.glb`의 위치**: 문서는 루트라고 했지만 실제로는 `assets/Scene.glb`입니다.

  지도를 **자기 도메인에 따로 올리기로** 하면서 사본이 필요해졌습니다 — Vercel의 Root
  Directory는 그 폴더 밖의 파일을 배포에 포함하지 않습니다. 지금은 `statistics/assets/`에
  사본을 두고, 코드가 후보 두 경로를 순서대로 시도합니다. 드리프트는 `sync-model.mjs`로
  막습니다(위 "Vercel 배포" 참고).
- **배의 폴리곤 수** (2026-09-27 GLB 기준): 배 몸체는 **1,396 tri**, 4조각(선체·캐빈·굴뚝·
  굴뚝 받침)입니다. 키워드 요소는 39(클로버)~1,472(갈매기) tri이고, 그 요소를 단 배만
  그립니다. 배 46척·요소 74개일 때 화면 전체가 약 211,000 tri, draw call 16입니다
  (몸체 4 + 쓰이는 요소 10 + 바다·하늘). 문서의 "282 tri / 22,560 tri" 추정보다는 한 자리
  크지만 현대 GPU에는 여유가 있습니다.
- **키워드 목록**: 시안 스크린샷에는 `비용`이 있지만 온보딩(`../index.html`)의 실제
  `KEYWORDS`에는 없습니다. 집계가 갈라지면 안 되므로 온보딩 쪽을 정본으로 삼았습니다.
- **바다 색은 팔레트에서 떼어낼 수 없습니다.** 하늘 4단 그라디언트·안개·조명 색·세기·수면
  반사색·노출이 시간대마다 한 세트로 묶여 있습니다(`TIME_OF_DAY`). 바다만 밝은 하늘색으로
  바꾸면 남색 하늘 아래 청록 바다가 뜹니다. 그래서 "설문 페이지의 기본 바다색"을 맞추는
  방법은 세트 자체를 설문과 같은 `day`로 두는 것이고, 그 결과 바다가 정확히 `#2fb3e6`이
  됩니다.
- **강조색은 금색 하나입니다.** 설문 B′는 어둠 위에 `--b-gold #E6C79A` 하나만 쓰고(고른 것 ·
  진행), 지도도 같습니다. `tokens.css`에는 예전 톤의 `--gold #b89a6a`(밝은 바탕용)·`--gold2`도
  남아 있지만 지도는 이제 쓰지 않습니다.
- **[예전 GLB] `Cabin` 노드에 재질이 없었습니다.** 지금 GLB는 굽기 단계에서 크림색 비금속
  재질(`Material_0`)을 채워 두므로 아래 증상은 없습니다. 모델을 다시 뽑다 재질이 또 빠질 수
  있어서 `fleet.js`에 안전장치는 남겨 뒀습니다(모든 그룹에 적용). 당시 기록:
  GLB에 재질이 없으면 GLTFLoader가 기본 재질을 만들어
  주는데, 그 기본값이 `metalness: 1`(완전 금속)입니다. 금속은 확산광이 없고 환경맵 반사만
  보이는데 이 씬에는 환경맵이 없어서, 직사광이 강한 낮에는 색이 스페큘러로 어른거리다가
  **밤 팔레트에서는 캐빈이 통째로 새까매집니다** — 즉 "키워드 → 캐빈 색" 규칙이 기본
  설정에서 아무 일도 안 합니다. 누가 의도해서 칠한 재질이 아니라 로더의 기본값이므로,
  **캐빈 그룹에 한해** `metalness: 0`으로 되돌렸습니다(색·지오메트리는 그대로).
  **온보딩 씬(`../index.html`)에도 같은 증상이 잠재해 있습니다** — 거기는 밝은 시간대가
  기본이라 아직 드러나지 않았을 뿐이고, 사용자가 '나눈 적 없음'을 골라 밤이 되면
  캐빈 색이 사라집니다. 온보딩 쪽은 이번 작업 범위 밖이라 건드리지 않았습니다.
- **`instanceColor`는 `material.vertexColors = true` 없이는 조용히 버려집니다.**
  three.js의 `color_vertex` 청크는 `USE_INSTANCING_COLOR`만으로도 `vColor`를 채우지만,
  `color_fragment` 청크는 `USE_COLOR`(= `vertexColors`)일 때만 그 값을 곱합니다.
  그리고 `vertexColors`를 켜면 지오메트리의 `color` 어트리뷰트도 같이 읽으므로,
  전부 1인 어트리뷰트를 깔아 둬야 새까매지지 않습니다. 둘 다 `fleet.js`에 주석으로 남겼습니다.

## 리퀴드 글래스

문서 9장의 2단계 구성을 그대로 따랐고, 강등 경로를 하나 더 붙였습니다.

| 단계 | 내용 | 언제 |
|---|---|---|
| `lens` | `blur(16px) saturate(1.55) url(#liquid-lens)` — `feDisplacementMap` 굴절 | Chromium 계열 기본 |
| `blur` | `blur(18px) saturate(1.6)` | Safari/Firefox는 `@supports`가 걸러서 자동으로 여기 |
| `flat` | `backdrop-filter` 없이 불투명 배경 | 프레임이 계속 모자랄 때 |

- 필터에 `color-interpolation-filters="sRGB"`가 붙어 있습니다. 없으면 노이즈가 선형
  색공간에서 생성돼 중간값이 0.5에서 밀리고, 결과가 굴절이 아니라 한쪽으로 쏠린
  평행이동이 됩니다.
- 유리는 투명 유리가 아니라 **어둠(설문 B′의 어둠 색 `rgba(7,9,14)`)을 한 겹 깐 유리**입니다.
  뒤가 매 프레임 변하는 바다 셰이더라 투명한 유리만으로는 파도가 글자 사이로 지나가 읽히지 않습니다.
  유리는 가운데 통계 카드에만 씁니다. 위쪽 제목과 아래 문장은 설문처럼 그라데이션 어둠 위에 얹습니다.
- 안개를 온보딩보다 훨씬 멀리 밀었습니다(near 40 / far 150). 수평선까지 바다가 이어져야
  하고(화면 28%), 유리 뒤가 균일한 안개색 판이면 굴절도 블러도 보일 게 없습니다.

**성능**: 워치독이 실제 벽시계 기준으로 프레임타임을 재고 자동으로 내려갑니다.
(`dt`에 0.05 상한이 걸려 있어서 장면 시간으로 재면, 렉이 심할수록 절전이 늦게 켜지는
정확히 반대 방향의 동작이 됩니다 — 그래서 워치독만 raw dt를 씁니다.)
1차는 온보딩과 같은 기준(33fps 미만)으로 스펙큘러·물결을 끄고 픽셀비를 1로 낮춥니다.
