# 머무름의 지도 (statistics/)

참여자들이 남긴 문장이 배 한 척씩으로 바뀌어 한 바다에 모이는 **전시용 송출 화면**입니다.
루트의 온보딩 씬(`../index.html`)이 "참여자 1명이 자기 배 1척을 보는 화면"이라면, 이 화면은
그 배들이 전부 모여 있는 화면입니다.

```
statistics/
├─ index.html        화면 골격 · importmap · 리퀴드 글래스 SVG 필터
├─ css/panel.css     상단 패널(리퀴드 글래스) · 타이포 · 반응형
└─ js/
   ├─ config.js      상수 전부 (원본에서 가져온 값 / 지도 전용 값이 구분돼 있음)
   ├─ ocean.js       파도 셰이더 + waveHeightAt  ← 온보딩 씬에서 그대로 확장
   ├─ fleet.js       Scene.glb의 Ship 노드를 InstancedMesh로
   ├─ style.js       "답변 → 배의 모습" 매핑이 있는 유일한 곳 (지금은 난수)
   ├─ motion.js      푸아송 디스크 배치 + 흐름
   ├─ camera.js      고정 카메라
   ├─ panel.js       누적 수 · 통계 자동 전환 · 새 문장 카드
   ├─ store.js       기록 저장소 (지금은 목업, 백엔드 어댑터 자리 있음)
   ├─ selfcheck.js   조용히 깨지는 것들 자동 점검
   └─ main.js        조립 + 프레임 루프
```

## 실행

`file://`로 열면 GLB fetch가 CORS로 막힙니다. 로컬 서버가 필요합니다.

```bash
python3 -m http.server 8000      # 레포 루트에서
# → http://localhost:8000/statistics/
```

GitHub Pages에 올라가 있으면 `/statistics/` 경로로 바로 열립니다.

### 쿼리 파라미터

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `time` | `night` | 시간대 팔레트 (`day` / `afternoon` / `evening` / `night`) |
| `glass` | (자동) | 유리 단계 고정 (`lens` / `blur` / `flat`). 안 주면 워치독이 판단 |
| `debug` | – | `1`이면 fps·draw call·인스턴스 수 오버레이 |
| `interactive` | – | `1`이면 드래그로 시점 조작 (리허설용, 전시 기본값은 무조작) |
| `seed` | `46` | 목업: 시작할 때 이미 쌓여 있는 기록 수 |
| `interval` | `14` | 목업: 새 기록이 들어오는 평균 간격(초). `0`이면 안 들어옴 |

전시장에서는 `?glass=...`로 유리 단계를 **박아두는 걸 권합니다**. 워치독은 안전장치이지
매번 같은 판단을 한다는 보장이 없어서, 실기기에서 한 번 재보고 고정하는 쪽이 예측 가능합니다.

## 인수인계 문서에서 미결정이었던 것들 — 이번에 정한 것

| 항목 | 결정 | 근거 |

| 인스턴싱에서 배 색 | **GLB 메쉬 노드마다 InstancedMesh 하나. 인스턴스 행렬은 공유, 색을 쓰는 그룹에만 `instanceColor`** | "배당 색 1개"의 제약도 "메쉬 쪼개기"의 수고도 없이 둘 다 얻음. 선체·굴뚝 재질은 GLB 원본 그대로 유지되고, draw call은 배 수와 무관하게 재질 수(9)로 고정 |
| 카메라 | **고정 (무조작)** | 전시장 TV/프로젝터에 입력장치가 없음. 배가 흐르는 연출이라 카메라까지 움직이면 "화면 끝에서 등장 → 반대쪽 퇴장" 규칙이 깨짐. `?interactive=1`로 리허설용 조작만 열어둠 |

| 백엔드 | **아직 안 정함** | 아래 "남은 일" 참고 — 계정·비용이 걸린 결정이라 코드로 앞서가지 않았음 |
| `age_bracket` | **안 건드림** | 미확정. 화면 쪽은 필드가 생기면 통계 지표 하나 추가하면 끝나는 구조(`panel.js`의 `METRICS`) |

### 흐름 — 배는 어떻게 움직이나

배는 **전부 같은 방향으로, 같은 속도로** 흐릅니다. 화면 왼쪽 끝에서 나타나 오른쪽으로
빠지고, 띠 폭(`FLOW_CORRIDOR_W = 80`)을 다 지나면 반대편 끝으로 감겨 다시 들어옵니다.

속도는 상수로 박지 않고 **"기준 깊이의 배가 40초에 화면을 건넌다"**로 정의하고
카메라 화각에서 역산합니다(`FLOW_CROSS_SEC`, `FLOW_REF_DEPTH`). 화면 폭은 기기
화면비마다 다르기 때문입니다. 세로 화면(1080×1920) 실측:

| 카메라 앞 거리 | 화면 가로 폭 | 횡단 시간 |
|---|---|---|
| 10 (화면 아래끝) | 6.5 | 24초 |
| 15 | 8.6 | 32초 |
| **20 (기준)** | **10.9** | **40초** |
| 30 (화면 세로 중앙) | 15.7 | 58초 |
| 48 (가장 먼 배) | 24.6 | 90초 |

속도를 하나로 통일한 게 핵심입니다. **깊이마다 속도를 달리 주면 원근이 사라져
평면 스크롤처럼 보입니다.** 가까운 배가 빨리, 먼 배가 천천히 지나가는 게 깊이감입니다.
띠 폭이 화면보다 넉넉해서 감기는 순간은 언제나 화면 밖이고, `selfcheck.js`가 이걸
화면비마다 검산합니다.

한 번에 화면에 보이는 배는 80척 중 약 13척입니다. 나머지는 띠의 화면 밖 구간에 있고,
약 5분 주기로 다시 들어옵니다.

### 표현 채널 — 지금은 난수

어떤 답변이 배의 무엇을 바꿀지가 아직 확정되지 않아서, **채널 값을 실제 답변이 아니라
난수에서 뽑고 있습니다.** `config.js`의 한 줄로 바뀝니다:

```js
export const STYLE_SOURCE = "random";   // "random" | "record"
```

난수는 `record_id`를 시드로 한 **고정 난수**입니다 — 매 프레임 새로 뽑으면 색이 깜빡이고,
매 로드마다 새로 뽑으면 전시 중 재시작할 때 바다가 통째로 달라집니다. 지금 방식이면
"그 기록의 배"는 언제 봐도 같은 배입니다.

**중요**: 난수인 건 **배의 모습뿐**입니다. 상단 패널의 누적 수와 통계(키워드·상태·지역
분포)는 지금도 실제 기록에서 집계합니다.

| 채널 | 어떻게 | 비용 |
|---|---|---|
| 캐빈 색 | `instanceColor` (재질 색을 흰색으로 두고 색 전체를 인스턴스가 들고 감) | 공짜 |
| 선체 색조 | `instanceColor` (GLB 원본 색에 흰색 근처 색조를 곱함 — 원본 색을 안 버림) | 공짜 |
| 갑판 소품 | 갈매기 / 구명튜브. 파츠마다 인스턴스 그룹 1개 | draw call +1씩 |

매핑을 바꾸거나 채널을 늘릴 때 손대는 파일은 **`style.js` 하나**입니다. 새 채널에
인스턴스 컬러를 걸려면 `fleet.js`의 `TINT_ROLES`에 한 줄만 더하면 됩니다.
씬·카메라·패널 코드는 "배마다 style 객체 하나"만 알고, 그 안이 어떻게 정해졌는지는
모릅니다.

### 상태별 자리·움직임은 어디 갔나

처음 판에는 상태(머무르는 중 / 떠날 준비 중 / 오가는 중 / 돌아온 사람 / 아직 모르겠음)에
따라 바다 중심에서의 거리와 움직임이 달랐습니다. 채널 구성이 아직 변동될 수 있다고 해서
**흐름 하나로 단순화하고 잠시 뺐습니다.** 되살릴 자리는 `motion.js`의 `stepBoat` 한 곳이고,
깊이나 속도 배수를 `style.js`가 정하게 하는 방법도 있습니다.

## 온보딩 씬에서 가져온 것 / 바꾼 것

**그대로 가져온 것** — Gerstner 파도 3개(파장 2.2/1.3/0.8)와 그 상수, 플랫 셰이딩(`dFdx/dFdy`),
프레넬+램버트+스펙큘러 조합, 안개, 물결(리플)·항적 셰이더, 무한 바다 재중심 트릭,
`WAVE_WRAP_DOMAIN` 랩, 성능 워치독 패턴, `Scene.glb`의 Ship 노드와 그 재질,
키워드→색/소품 매핑, 시간대 팔레트.

**바꾼 것 (3곳뿐입니다)**

1. **재중심이 1축 → 2축.** 온보딩은 배가 +X로만 나아가서 `uBoatX`(float) 하나면 됐습니다.
   지도는 카메라가 XZ 평면을 자유롭게 흐르므로 `uCenter`(vec2)로 바꿨습니다. 수식은 그대로입니다.
   `WAVE_WRAP_DOMAIN = 1144`가 Z축에서도 공배수인지 검산해 봤고, 맞습니다
   (X: 520/440/1001, Z: 78/748/572 — 전부 정수). `selfcheck.js`가 로드마다 다시 검산합니다.
2. **유리병 클리핑(`uClip*`) 제거.** 지도엔 병이 없습니다.
3. **스케일·카메라·인스턴싱 구조.** 배 크기 3.38 → 1.5, FOV 34 → 50, 타일 31.5 → 190,
   안개 범위 확대. 재질·색·지오메트리는 손대지 않았습니다.

## 알아둘 것 — 인수인계 문서와 실제가 다른 점

- **`Scene.glb`의 위치**: 문서는 루트라고 했지만 실제로는 `assets/Scene.glb`입니다.
  `statistics/`에 복사하지 않고 `../assets/Scene.glb`로 참조합니다 — 모델을 다시 구우면
  온보딩과 지도가 저절로 같이 갱신되고(진실의 출처가 하나), 345KB짜리 이진 파일이
  레포에 두 벌 들어가지 않습니다. 같은 오리진이라 CORS 문제도 없습니다.
- **배의 폴리곤 수**: 문서는 282 tri라고 했지만 실제 Ship 노드는 **1,302 tri**입니다
  (Ship Body 1226 + Funnel 40 + Funnel step 24 + Cabin 12). 갈매기(1,472)와 튜브(312)까지
  더하면 배 1척이 최대 3,086 tri, 80척이면 약 247,000 tri입니다. draw call이 9로 고정이라
  현대 GPU에는 여전히 여유가 있지만, 문서의 "22,560 tri" 추정보다 한 자리 큽니다.
- **키워드 목록**: 시안 스크린샷에는 `비용`이 있지만 온보딩(`../index.html`)의 실제
  `KEYWORDS`에는 없습니다. 집계가 갈라지면 안 되므로 온보딩 쪽을 정본으로 삼았습니다.
- **GLB의 `Cabin` 노드에는 재질이 없습니다.** 그러면 GLTFLoader가 기본 재질을 만들어
  주는데, 그 기본값이 `metalness: 1`(완전 금속)입니다. 금속은 확산광이 없고 환경맵 반사만
  보이는데 이 씬에는 환경맵이 없어서, 직사광이 강한 낮에는 색이 스페큘러로 어른거리다가
  **밤 팔레트에서는 캐빈이 통째로 새까매집니다** — 즉 "키워드 → 캐빈 색" 규칙이 기본
  설정에서 아무 일도 안 합니다. 누가 의도해서 칠한 재질이 아니라 로더의 기본값이므로,
  **캐빈 그룹에 한해** `metalness: 0`으로 되돌렸습니다(색·지오메트리는 그대로).
  **온보딩 씬(`../index.html`)에도 같은 증상이 잠재해 있습니다** — 거기는 밝은 시간대가
  기본이라 아직 드러나지 않았을 뿐이고, 사용자가 '나눈 적 없음'을 골라 밤이 되면
  캐빈 색이 사라집니다. 온보딩 쪽은 이번 작업 범위 밖이라 건드리지 않았습니다.
- **`instanceColor`는 `material.vertexColors = true` 없이는 조용히 버려집니다.**
  three.js의 `color_vertex` 청크는 `USE_INSTANCING_COLOR`만으로도 `vColor`를 채우지만,
  `color_fragment` 청크는 `USE_COLOR`(= `vertexColors`)일 때만 그 값을 곱합니다.
  그리고 `vertexColors`를 켜면 지오메트리의 `color` 어트리뷰트도 같이 읽으므로,
  전부 1인 어트리뷰트를 깔아 둬야 새까매지지 않습니다. 둘 다 `fleet.js`에 주석으로 남겼습니다.

## 리퀴드 글래스

문서 9장의 2단계 구성을 그대로 따랐고, 강등 경로를 하나 더 붙였습니다.

| 단계 | 내용 | 언제 |
|---|---|---|
| `lens` | `blur(16px) saturate(1.55) url(#liquid-lens)` — `feDisplacementMap` 굴절 | Chromium 계열 기본 |
| `blur` | `blur(18px) saturate(1.6)` | Safari/Firefox는 `@supports`가 걸러서 자동으로 여기 |
| `flat` | `backdrop-filter` 없이 불투명 배경 | 프레임이 계속 모자랄 때 |

- 필터에 `color-interpolation-filters="sRGB"`가 붙어 있습니다. 없으면 노이즈가 선형
  색공간에서 생성돼 중간값이 0.5에서 밀리고, 결과가 굴절이 아니라 한쪽으로 쏠린
  평행이동이 됩니다.
- 가이드의 `rgba(255,255,255,.08)` 위에 **어두운 스크림을 한 겹 깔았습니다.** 뒤가 밤바다
  셰이더라 흰 유리만으로는 파도가 글자 사이로 지나가 읽히지 않습니다. 스크림은 아래로
  갈수록 진해집니다 — 패널 위쪽 뒤에는 안개·하늘(어둡고 균일), 아래쪽 뒤에는 바다
  (밝고 어른거림)가 오기 때문입니다.
- 안개를 온보딩보다 훨씬 멀리 밀었습니다(near 34 / far 84). 유리 뒤가 균일한 안개색 판이면
  굴절도 블러도 보일 게 없어서 그냥 어두운 색판이 됩니다. 먼 바다의 결이 비쳐야 유리로 읽힙니다.

**성능**: 워치독이 실제 벽시계 기준으로 프레임타임을 재고 자동으로 내려갑니다.
(`dt`에 0.05 상한이 걸려 있어서 장면 시간으로 재면, 렉이 심할수록 절전이 늦게 켜지는
정확히 반대 방향의 동작이 됩니다 — 그래서 워치독만 raw dt를 씁니다.)
1차는 온보딩과 같은 기준(33fps 미만)으로 스펙큘러·물결을 끄고 픽셀비를 1로 낮춥니다.
2차부터는 유리를 한 단계씩 내립니다.

## 남은 일

1. **백엔드 (제일 큰 덩어리).** 지금은 `MockStore`가 가짜 기록을 만들어 냅니다.
   화면이 저장소에 요구하는 건 세 가지뿐입니다 — `onReady(records)` / `onInsert(record)` /
   `onRemove(recordId)`. `store.js`에 Supabase·Firestore 두 경우의 배선이 주석으로 적혀 있고,
   정해지면 `main.js`의 저장소 한 줄만 갈아끼우면 씬 쪽은 손댈 게 없습니다.
   - 어느 쪽이든 **공개 조건(`consent_public` && `moderation_status === "public"`)은
     서버에서 걸어야 합니다.** 비공개 문장이 브라우저까지 내려온 뒤 JS가 거르는 구조면
     개발자도구만 열면 다 보입니다.
   - Firestore를 쓴다면: 첫 스냅샷이 기존 문서 전부를 `added`로 줍니다. 그대로 두면
     시작할 때 수십 척이 한 척씩 등장 연출을 하며 쏟아집니다. 첫 스냅샷만 모아서
     `onReady`로 넘겨야 합니다.
2. **관리자 화면** (문장 숨김·금칙어 확인). 화면 쪽은 `onRemove`만 받으면 즉시 반영됩니다.
3. **인터넷 장애 대비** 임시 로컬 저장·재전송. 제출 쪽(온보딩) 몫입니다.
4. **실기기 프레임 측정.** 전시장에서 쓸 TV/태블릿에서 `?debug=1`로 한 번 재보고
   `?glass=`를 고정할 것. Chromium 계열이 아니면 굴절은 자동으로 꺼집니다.
5. **표현 채널 확정.** `STYLE_SOURCE`를 `"record"`로 바꾸고 `style.js`의 `fromRecord`
   쪽을 채우면 됩니다. 지역 → 선체 색조 매핑은 자리만 비워 뒀습니다.

   숫자의 인상이 달라질 수 있어서, 웹폰트를 쓸 거면 오프라인 대비로 파일을 레포에
